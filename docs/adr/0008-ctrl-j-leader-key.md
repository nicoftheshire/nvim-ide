# Use `<C-j>` as the leader key, not `<Space>`

Charting originally settled `<Space>` as the leader key, informally, before any keybinding scheme existed to test it against. Grilling ticket 05 reopened that choice: the user's personal `~/.tmux.conf` already uses `C-j` as the tmux prefix, so making nvim-ide's leader the same chord means one muscle-memory gesture means "I'm about to issue a command" in both tools, rather than two different ones. This also sidesteps a problem `<Space>` had — neo-tree.nvim's default `git_status`/`filesystem` window mapping binds bare `<space>` to `toggle_node`, which would otherwise swallow every `<leader>`-prefixed keymap while the Sidebar has focus.

This only works because nvim-ide runs as the top-level terminal app on the local macOS machine, not nested inside a tmux pane — tmux's prefix handling intercepts the raw keystroke at the multiplexer level before any inner program sees it, and this tmux.conf binds `h`/`j`/`k`/`l` directly under the `C-j` prefix, so a nested Neovim would never receive `<leader>` followed by a navigation key at all. On the Linux box reached over SSH (ticket 07), nvim-ide is instead wrapped in a vanilla tmux session with stock settings (default `C-b` prefix, not this personal config) purely for SSH-disconnect resilience; since that instance's prefix isn't `C-j`, there's no collision there either.

Vim-style window navigation (Chrome Navigation Mode) is `<leader>` then `h`/`j`/`k`/`l` — not a bare `<C-h/j/k/l>` — deliberately mirroring the tmux prefix+hjkl gesture rather than the more common standalone-Ctrl Neovim convention.
